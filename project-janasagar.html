Janasagar v2

Janasagar is a live community platform. It helps users build a strong profile, bond with friends, and earn points for genuinely helping others find the right direction.

Role
Solo full-stack developer
Type
Four apps, one backend

01 What it does

A community platform, built for real people.

I built Janasagar around a simple idea: useful questions and answers should help people find each other. Profiles, articles, and groups give those conversations a place to grow.

Build your profile

Create a strong profile, write articles, share what you know, and grow your own space in the community.

Build bonds with friends

Join groups, accept rules, connect with people you trust, and invite others who share your interests.

Points for genuine help

Good contributions earn points. When your answers help others find the right direction, your profile stands out.

Questions and articles

Ask anything, write rich text posts, mark accepted answers, and give feedback on every post and comment.

Search people and posts

Find groups, articles, and users with ranked results and fast suggestions.

Safe login

Email and Google login, optional two factor, hashed email tokens, and short sessions keep your account secure.

02 How it works

Nine decisions that matter.

Feeds, abuse control, and what happens when a dependency fails. Short notes on each.

01 / FEEDS

Home feed with two paths

feeds

Small groups get a feed row for every member when a post is created. That is fan-out on write. It uses one insert and unique keys, so a retry is safe.

Large groups build the feed when someone opens the page. That is fan-out on read. If a queue job is ever lost, the second path still finds the post. A lost job must never hide a post.

Two feed paths Safe to retry Never hides a post
02 / DATA

Fast pages with keyset cursors

data

Lists page with keyset cursors, not offset. Deep pages stay fast because the database jumps straight to the next row. Models use Drizzle ORM for typed queries, and the hot feed reads drop to raw SQL.

Cursors are opaque and checked before use. A test suite pages every tab at every size to prove there are no gaps and no repeats.

0.03ms cursor lookup Few rows per page Zero gaps in tests
03 / ABUSE

27 rate limit rules

abuse control

One small library holds 27 named rules across three counting methods: fixed windows, sliding windows, and a token bucket. The same logic runs in memory and in Redis, so both give the same answer.

Login checks are stacked: IP plus email, then device, then IP alone. Only failed tries count, and a success refunds the budget. Every 429 response states the limit, what is left, and when to retry.

27 named rules 0.6ms refusal path Clear 429 headers
04 / CACHE

Keeping shared caches separate from user data

caching

Every cache fails open. If Redis goes down, pages get slower but stay correct. One shared version number clears all list caches at once, with no key scan.

Single flight means a cache miss causes one rebuild, not many. User data such as votes and joined groups is added after the cache, on a copy. One user's data never leaks into another user's page, which also shuts down cache poisoning.

One version number One rebuild per miss Fail open caches
05 / AUTH

Login and session safety

auth

Refresh tokens are random secrets stored only as hashes. Every use rotates the token. If an old token comes back, the whole token family is revoked. That is a direct answer to session hijack.

Access tokens last 15 minutes. Logout adds the token to a deny list. The login path takes the same time whether or not an account exists, so it cannot be used to find emails. Two factor is optional.

Hash only tokens at rest Reuse revokes family 15 min access token
06 / INPUT

Strict input checks

security

Schemas are strict. AJV validation rejects unknown fields and prototype pollution attacks at the edge, before any handler runs. Rich text passes an allow list, so scripts and bad links cannot be saved.

Free text is normalized and stripped of control characters and hidden text tricks. A same origin guard returns 403 on cross site writes before login or validation runs. The content security policy uses a fresh nonce on every response.

AJV strict schemas Allow list for HTML New nonce per response
07 / QUEUES

Eight queues and live updates

async

Eight RabbitMQ queues carry slow side work: email, feed fan-out, cache warming, and image processing. Messages are saved to disk. A failed message gets one retry, then goes to a dead letter queue. Queue depth alerts fire at boot.

Comment events also feed live SSE streams, so open pages update without polling. New posts pre-warm the first page of each feed off the request path.

8 queues 1 retry, then dead letter SSE live updates
08 / FILES

Uploads that skip the API

files

Images go from the browser straight to private storage with a short lived signed URL. The API never touches the bytes. The request is checked against a strict type list and storage names come from server side IDs.

A worker decodes each file, rejects animated formats and zip bombs, strips metadata, and resizes it. If the owner does not match, the response is 404, not 403, so IDs cannot be guessed.

0 bytes through the API Clean re-encode 404 against probing
09 / AI

A bot with guards

ai

The bot turns public sources into posts. Untrusted text is fenced as data, so injected instructions stay inert. Output is checked by schema and again by code. Titles are length checked, duplicates are blocked, and links must be https.

A scheduler spreads posts across the day with spacing and jitter. It backs off when the source API asks it to slow down. Dry runs, pause and resume, and live logs are all available from a small local panel.

Fenced untrusted text Two output gates Dry run first
