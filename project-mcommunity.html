MCommunity v1

MCommunity is a live anonymous chat and video app. Users connect with strangers and create rooms for anonymous chat. Clients can also buy ad slots to reach the community.

Role
Solo full-stack developer
Type
Live chat and video
Core stack
WebSocket, WebRTC, LiveKit, Redis, Next.js
Database
None. Temporary state only
01 What it does

Anonymous chat and rooms, built for real connection.

This platform lets users connect with strangers at random, open rooms for anonymous chat, and play games together. Clients can also buy ad slots to show their message to the community.

Connect with strangers

Pick a nickname and get matched at random for video or text chat. Filters for gender, country, language, and interests help you meet the right people.

Create rooms for chat

Open a temporary room by link, invite strangers, and keep the chat private. The room closes when the owner leaves.

Video or text only

Camera users and text only users are matched in separate pools. The two modes never meet.

Ludo in chat

A two to four player game with captures, safe cells, and exact finishes. The server holds the truth.

Face effects

Browser based face tracking drives live camera overlays. Video frames never leave the device.

Ad slots for clients

Clients can buy ad slots to show their message to the community and reach active users.

Anonymous by design

A new identity per session. No profile, no history. State expires, so there is nothing left to leak.

Honest presence

The online counter is a real count. Any display number that is not real is labelled and tested.

02 How it works

Real time problems, solved.

Around 35 socket events, live media, and no database to fall back on. Each choice below exists because something can fail.

01 / MEDIA

WebRTC that handles glare

media

The peer connection uses perfect negotiation in one hook. One side is polite and the other is not. If both send an offer at the same time, the polite side yields, so the call does not deadlock. Trickle ICE keeps media moving during renegotiation.

Signaling runs on its own socket path. Relay credentials are short lived and signed, so a leaked credential expires on its own.

Polite and impolite roles Trickle ICE Expiring relay credentials
02 / MEDIA

Mesh for small calls, LiveKit for large rooms

media

One to one calls and small rooms use a direct WebRTC mesh. Each browser sends its stream to the others, with no media server in the middle. That is cheap and fast for a few people.

Large rooms switch to LiveKit, which is an SFU. Each browser uploads once and LiveKit forwards the streams. The switch happens at runtime when a media token is present, and the app falls back to mesh if LiveKit is not available.

Mesh for one to one LiveKit for large rooms Runtime switch
03 / MATCHING

Matchmaking with a score

algorithm

Hard rules decide who can meet: mode, gender, and country preferences. A soft score then ranks the people who pass. Shared language, shared country, and shared interests all add points.

Waiting pools are sorted sets with timestamps. Old entries are removed by range, not by scanning every key. First come first served breaks ties, and a fallback stops two people waiting for a third.

Score based match Sorted waiting pools FIFO fairness
04 / STATE

No database, only TTL state

data

There is no SQL database and no ORM. All state goes through a small key value layer with two backends: memory and Redis. Every record has a time to live, and a per key lock keeps changes in order.

Going from one server to many is an environment change. Use the Redis backend, share the socket adapter, and share the rate limit store. No code changes.

Memory or Redis TTL on every record Per key locks
05 / ABUSE

Moderation that resists griefing

security

Serious reports need several different reporter IPs before anything happens. One angry user cannot remove a stranger. Small reports need repeated strikes inside a time window, and each IP has an hourly report budget.

Private and loopback addresses are skipped. IPs are not written to logs. Short bans expire on their own. Production refuses to start if the relay setup would expose credentials.

Several IPs for serious reports Hourly report budget No IP logs
06 / SOCKETS

WebSocket safety

security

The socket handshake checks the origin and refuses the upgrade if it is wrong. Frames are capped at 256 KB to limit abuse. Proxy headers are read right to left with a trusted hop count, so a client cannot fake an IP and skip limits.

Each event has its own rate budget. Signaling events get more, typing events get less. There is also a per IP connection cap at handshake time.

256 KB frame cap Right to left proxy parsing Per event budgets
07 / GAME

A game you can test

craft

Ludo is a pure engine. It handles the shared ring, base exits, captures, safe cells, exact finishes, and extra rolls on a six. The server owns the state and keeps it across reconnects. The client only draws what the server decides.

Because the engine is pure, the tests cover every rule, including invite expiry races. The 3D dice are plain CSS.

Pure testable core Kept on reconnect CSS 3D dice
08 / SCALE

Load control in layers

scale

Hot reads use a short cache where many misses share one rebuild. Cache headers let the edge absorb the rest. Background jobs queue only one deep. Extra jobs are dropped and counted instead of piling up.

A waiting pool cap slows new users before the queue grows. Socket events have their own budgets, and each IP has a connection cap. Queue depth and pool size are visible on a protected status route.

Shared rebuilds Bounded job queue Live load stats
